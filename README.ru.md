# OpenFlux

[English](README.md) | **Русский**

Исследовательский инструмент сетевого стека. TCP-туннель с подключаемыми
транспортами, батчированным zstd-кодеком и двумя бэкендами выходной ноды
(L3 raw forward / L4 gVisor proxy).

## Об этом форке

Форк [p1neappleXpress/OpenFlux](https://github.com/p1neappleXpress/OpenFlux)
(на основе `0.0.3`), объединяющий собственные наработки этого форка с
доработками, взятыми из форка сообщества
[danusha2345/OpenFlux](https://github.com/danusha2345/OpenFlux), и несколько
отдельных PR из апстрима. В паре с
[форком Android-клиента](https://github.com/Kingofthedivanich/OpenFluxAndroid),
который следует за изменениями шифрования этого репозитория.

**Шифрование и идентификация**
- **Шифрование Noise NKpsk0** (X25519 + AES-256-GCM, ротация сессионных
  ключей) заменило старое статическое AES-GCM-шифрование транспорта;
  включено по умолчанию, если не передан `--allow-plaintext`. См.
  [Шифрование](#шифрование-опционально).
- **`netguard`** — деннилист SSRF: по умолчанию выходная нода блокирует
  приватные/loopback/link-local адреса и cloud-metadata (`--allow-private`
  отключает).

**Мультиклиентская выходная нода**
- **Локальная веб-панель управления** (`--role=exit-panel`) — несколько
  клиентов в одном процессе, у каждого свой Yandex.Docs / Volga / MAX /
  Cups.online / Mail.ru документ или комната; управление «на лету»
  (добавление, редактирование, удаление, статус, трафик, публичный ключ
  панели — скопировать одной кнопкой), без перезапуска. Все клиенты
  используют общий Noise-идентификатор панели; файл PSK у конкретного
  клиента опционально закрывает именно его от посторонних. Кнопка QR на
  карточке клиента импортирует его в Android-приложение одним сканом, а
  опциональный OAuth-токен Яндекса позволяет панели самой генерировать
  документ для `--url` вместо создания вручную. См.
  [Выходная нода - мультиклиентская панель](#выходная-нода---мультиклиентская-панель).
- **Telegram-бот администратора** (опционально, та же роль) — полный
  паритет с веб-панелью по управлению клиентами, работает с телефона без
  SSH-туннеля. См.
  [Telegram-бот администратора](#telegram-бот-администратора-опционально).
- **`deploy/menu.sh`** — интерактивная консоль на самом VPS в стиле меню
  3x-ui: обновление, управление клиентами, включение/перенастройка/
  отключение Telegram-бота — без ручного редактирования systemd-юнита. См.
  [Консоль управления](#консоль-управления-как-меню-в-3x-ui).

**Транспорт**
- **Multi-stream** — `--url` принимает список документов через запятую
  (yandex/vyandex, и у CLI, и у клиентов панели), соединения распределяются
  между ними с переключением на остальные при обрыве одного.
- **`--upstream-proxy`** — выходная нода может сама ходить в интернет через
  апстрим SOCKS5-прокси вместо прямого подключения.
- **Рандомизированные keep-alive Yandex.Docs** — случайный интервал и длина
  паддинга вместо пакета фиксированного размера с фиксированным интервалом —
  это отпечаток для traffic-анализа, переживающий даже TLS.
- **`--traffic-stats=<интервал>`** — периодическая машиночитаемая строка
  `[TRAFFIC] connected=%t tx=%d rx=%d` из настоящих счётчиков байт
  транспорта, для всего, что читает stdout процесса.

**Корректность и надёжность** — ~25 фиксов на стороне выходной ноды и
транспортов с момента форка, каждый с регрессионным тестом: две паники,
вызываемые удалённой стороной, decompression-bomb DoS, тихо игнорируемый
`--local-ip`, RST от клиента, не доходящий до реального сервера, утечка
памяти/горутин на зависших L4-реле, блокировка всей обработки пакетов на
время periodic-скана conntrack, отсутствие graceful shutdown по SIGTERM,
лимит записей conntrack, half-close на всех путях данных вместо жёсткого
закрытия, соответствие SOCKS5 RFC 1928, гонка данных без синхронизации при
реавторизации транспорта, `EncryptedTransport.IsConnected()`, сообщавший
`true` ещё до завершения Noise-хендшейка (реальное окно чёрной дыры для
пакетов), и фиксы реконнекта/keepalive в транспортах
Yandex/Volga/MAX/Mail.ru.

**Не поддерживается в этом форке**
- **iOS-мост** — `export_ios.go` собирается под `//go:build ios` (унаследован
  от апстрима/форка сообщества), но iOS-приложение и CI для него здесь не
  публикуются.
- `build_android.sh` учитывает ОС хоста (macOS/Linux/Windows) и собирает все
  три ABI, под которые
  [форк Android-приложения](https://github.com/Kingofthedivanich/OpenFluxAndroid)
  реально поставляет `jniLibs` — но само Android-приложение живёт в том
  отдельном репозитории.

## Архитектура

> **Шифрование включено по умолчанию** (Noise `NKpsk0`): запускайте выходную
> ноду с `--exit-key-file`, клиента с `--peer-key`, либо передайте
> `--allow-plaintext` для незащищённого туннеля. Все клиенты (десктоп, iOS,
> Android) используют кодек **batched** и один wire-формат.

Любой клиент работает с любым бэкендом выходной ноды. `--mode` выбирается
на **выходной ноде**, а не на клиенте.

```
Клиент (любой): macOS (utun) / Linux / Windows / iOS (packet tunnel) / Android
                    |
                    v
               Транспорт (Yandex.Docs / Volga / MAX / Cups / Mail.ru)
                    |
                    v
               Выходная нода  -->  Интернет
                 --mode l3   (сырой SNAT/DNAT, Linux + root)
                 --mode l4   (gVisor proxy, любая платформа)
```

| Клиент (любой)                          | Бэкенд выхода | Требует              |
|-----------------------------------------|---------------|----------------------|
| macOS / Linux / Windows / iOS / Android | `--mode l3`   | exit на Linux + root |
| macOS / Linux / Windows / iOS / Android | `--mode l4`   | ничего               |

В `l3` выходная нода ничего не терминирует: она форвардит сырые IP-пакеты
с SNAT/DNAT (conntrack + фильтр по egress-IP). Одно TCP-соединение
end-to-end между клиентом и реальным сервером.

В `l4` выходная нода терминирует TCP в userspace-стеке gVisor, затем
переподключается к реальному серверу через `net.Dial`. Работает на любой ОС
без root.

Клиент терминирует TCP локально (gVisor, utun или NEPacketTunnelProvider),
затем отправляет сырые IP-пакеты в транспорт.

## Бэкенды выходной ноды

У выходной ноды ровно **два** бэкенда, выбираются флагом `--mode` на
**выходной ноде**. Клиент бэкенд не выбирает - один и тот же клиент
работает с любым из них.

| `--mode` | Бэкенд | Форвардинг | Требует | Платформы |
|----------|--------|-----------|---------|-----------|
| `l3` | Сырой L3 | SNAT/DNAT сырых IPv4-пакетов через SOCK_RAW + conntrack. Без userspace TCP-стека. | root / CAP_NET_RAW | только Linux |
| `l4` (алиас `proxy`) | gVisor proxy | Терминирует TCP в userspace-стеке gVisor, затем `net.Dial` к реальному серверу. | ничего | Linux, macOS, Windows |

- `proxy` - устаревший алиас для `l4`; оба выбирают один и тот же бэкенд.
  Каноническое имя впредь - `l4`.
- **l3 быстрее** (одно TCP-соединение end-to-end, без двойной терминации),
  но только Linux и нужен root.
- **l4 работает везде** без root, ценой двойной терминации TCP
  (клиент -> gVisor на выходе -> реальный сервер).
- На Linux с root предпочитайте `l3`. На Windows целевой путь - `l3`
  внутри лёгкой QEMU-виртуалки (см. TODO); WinDivert-бэкенд пока не подключён,
  а `l4` - рабочий fallback, пока QEMU не поставлен. На хостах без root -
  `l4`.

### l3 и kernel-RST

В режиме `l3` ядро видит ответные пакеты для соединений, которые оно не
открывало, и шлёт RST, разрывая туннельные соединения. Их надо гасить:

```
# Scoped (рекомендуется): назначить отдельный egress-IP, запустить с --local-ip, затем:
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -s <egress-ip> -j DROP

# Host-wide fallback (дропает ВСЕ исходящие RST; закрытые порты выглядят filtered):
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -j DROP
```

Дополнительно код L3 сам дропает клиентские RST до `sendto()`, так что
правило выше нужно только для RST, которые генерирует ядро.

## Ключевые особенности

- **Подключаемые транспорты** - Yandex.Docs (WS), Yandex Volga (HTTP relay + WS),
  MAX/OneMe (WebRTC DataChannel), Cups.online (Centrifugo-комнаты),
  Mail.ru Docs (WS).
- **Батчинг + zstd** - склеивает множество туннельных пакетов в одно
  транспортное сообщение. Меньше сообщений в канале, выше скорость. См.
  `transport/batched.go` и `transport/framing.go`.
- **Два бэкенда выхода** - `l3` (сырой SNAT/DNAT) и `l4` (gVisor proxy).
  См. [Бэкенды выходной ноды](#бэкенды-выходной-ноды).
- **macOS utun-клиент** - `--inbound=tun` (по умолчанию на macOS). Создаёт
  utun-интерфейс, следит за своими сокетами и ставит bypass-маршруты, затем
  забирает default-маршрут. Никакого SOCKS5, никакого gVisor на клиенте.
- **iOS packet tunnel** - NEPacketTunnelProvider, чистый L3-форвардинг.
- **Legacy-кодек** - `--codec=legacy` возвращает старый per-packet LZ4-кодек
  (совместим со старыми клиентами).
- **Опциональное шифрование** - `--exit-key-file` на выходной ноде и
  `--peer-key` на клиенте запускают Noise-handshake `NKpsk0` (X25519 +
  AES-256-GCM) поверх канала; сессионные ключи ротируются каждые 2 минуты.
  `--psk-file` на обеих сторонах закрывает ноду от клиентов без секрета.
- **Режимы бенчмарка** - `--role=bench-send --bench-bytes=N` / `--role=bench-sink`
  измеряют чистый goodput через транспорт, не задевая сеть хоста.
- **Телеметрия трафика** - `--traffic-stats=<интервал>` логирует
  `[TRAFFIC] connected=%t tx=%d rx=%d` из настоящих счётчиков байт
  транспорта, для всего, что читает stdout процесса.

## Требования

1. **Go** - для сборки бинарника десктопного клиента / выходной ноды. Точная
   версия - в `go.mod`.
2. **Android NDK r27+** - для сборки нативной библиотеки
   [Android-клиента](https://github.com/Kingofthedivanich/OpenFluxAndroid)
   из этого репозитория.
3. **Linux VPS / VDS** для выходной ноды. Бэкенд `l3` требует root; `l4`
   работает без root.

Xcode нужен только для цели `export_ios.go` под `//go:build ios`, которую
этот форк не собирает и не публикует — пропусти, если не занимаешься этим
сам.

## Использование

### Выходная нода - L3 (Linux, root)

```
sudo ./openflux --role=exit --mode=l3 \
    --transport=yandex \
    --url="YOUR_YANDEX_DOC_URL"
```

Требует root / CAP_NET_RAW. Поставьте правило iptables (см.
[l3 и kernel-RST](#l3-и-kernel-rst)).

### Выходная нода - L4 (любая ОС, без root)

```
./openflux --role=exit --mode=l4 \
    --transport=yandex \
    --url="YOUR_YANDEX_DOC_URL"
```

Fallback для платформ, где `l3` недоступен (Windows без WinDivert, macOS,
Linux без root). Медленнее `l3` (двойная терминация TCP).

### Выходная нода - мультиклиентская панель

```
./openflux --role=exit-panel \
    --panel-addr=127.0.0.1:8088 \
    --panel-user=admin --panel-pass=CHANGE_ME \
    --panel-data=./clients.json --panel-key-file=./panel.key
```

Запускает много клиентов в одном процессе, у каждого свой транспорт (свой
документ/комната) и свой независимый туннель `l4` — трафик клиентов не
пересекается. Клиенты управляются «на лету» через локальную веб-панель по
адресу `--panel-addr` (добавление, редактирование, удаление, статус/трафик,
копирование публичного ключа панели) без перезапуска; регистрации
сохраняются в `--panel-data` и подхватываются при следующем запуске.
`--panel-addr` должен оставаться на `127.0.0.1`; подключайтесь удалённо
через SSH-туннель (`ssh -L 8088:127.0.0.1:8088 user@host`), а не открывайте
наружу напрямую. `l3` в этой роли намеренно не предлагается — см. обычный
`--role=exit` выше, если нужен сырой SNAT/DNAT.

Клиент cupsonline — особый случай: выходная нода сама создаёт комнаты,
поэтому в UI для него нет поля URL — сгенерированный список комнат (то, что
клиенту нужно как собственный `--url`) появляется на карточке этого клиента
после старта его транспорта.

`--panel-key-file` — собственный статический Noise-ключ панели, создаётся
при первом запуске и печатается в лог; все клиенты используют один и тот же
идентификатор, подключаясь с `--peer-key=<этот публичный ключ>`. При
добавлении клиента в веб-интерфейсе можно указать необязательный файл PSK,
закрывающий именно этого клиента от посторонних.

На карточке каждого клиента есть кнопка **QR**: отсканировав его кнопкой
«+» в Android-приложении, клиент импортируется и настраивается сам
(транспорт, url/токен, публичный ключ панели и PSK, если он есть) — без
ручного копирования.

#### Автосоздание документов Yandex.Docs (опционально)

```
./openflux --role=exit-panel \
    --panel-addr=127.0.0.1:8088 --panel-user=admin --panel-pass=CHANGE_ME \
    --yandex-token-file=./yandex.token
```

`--yandex-token-file` просто указывает, где хранить токен — файл не
обязан существовать заранее. С этим флагом под публичным ключом панели
появляется карточка, где токен можно задать, заменить или отключить прямо
из веб-интерфейса, без перезапуска в обе стороны. Как только токен задан,
у поля URL для клиентов **`vyandex`** в «Добавить клиента» появляется
кнопка **Сгенерировать**: она загружает пустой `.docx` на Диск этого
Яндекс-аккаунта, публикует его с правом редактирования для всех по
ссылке и подставляет публичную ссылку — не нужно создавать документ
вручную и копировать ссылку. Нажми ещё раз — добавится ещё один документ
этому же клиенту (multi-stream).

Работает это только для `vyandex`, не для обычного `yandex`: файл,
загруженный через Disk API, Яндекс всегда открывает через свой
WOPI/«Volga» онлайн-редактор — это ровно тот протокол, что использует
`--transport=vyandex`. `--transport=yandex` нужен документ, созданный
именно в самом интерфейсе Yandex Docs (другая, не-WOPI сессия
редактора, без публичного API), поэтому для него кнопки нет.

Токен — на [oauth.yandex.ru](https://oauth.yandex.ru/client/new): создай
приложение с правом «Яндекс.Диск REST API» (запись), затем открой
`https://oauth.yandex.ru/authorize?response_type=token&client_id=<id твоего приложения>`,
разреши доступ и вставь `access_token` со страницы результата в карточку
панели. Это тот же официальный Disk API, которым
пользуются настоящие приложения Яндекса — никак не связан с тем, как сам
`transport/yandex` работает с документом (неавторизованный скрапинг
публичной страницы редактора), так что токен нужен только для
создания/публикации документов и никогда не участвует в передаче трафика.

#### Telegram-бот администратора (опционально)

```
./openflux --role=exit-panel \
    --panel-addr=127.0.0.1:8088 --panel-user=admin --panel-pass=CHANGE_ME \
    --telegram-bot-token=<токен от @BotFather> \
    --telegram-admin-ids=<твой telegram user id>[,<ещё id>]
```

Запускает Telegram-бота в том же процессе, подключённого напрямую к тому же
менеджеру клиентов, что и веб-панель — полный паритет (`/list`,
`/status <id>`, `/key`, `/add`, `/edit <id>`, `/remove <id>`), так что
панелью можно управлять с телефона без SSH-туннеля. `/status <id>` также
присылает QR-код этого клиента отдельным фото — так же, как кнопка QR в
панели, для импорта в Android-приложение одним сканированием. Отвечает
только тем, чей id есть в `--telegram-admin-ids`, остальным — молча
игнорирует. Токен — у
[@BotFather](https://t.me/BotFather), свой id — у
[@userinfobot](https://t.me/userinfobot).

### Обновление развёрнутой выходной ноды

Каждый релизный тег публикует собранный `openflux-linux-amd64` (с зашитой
версией через `--version`) как ассет GitHub Release — см.
[`.github/workflows/release.yml`](.github/workflows/release.yml).
[`deploy/update.sh`](deploy/update.sh) скачивает последний релиз, ставит его
на место и перезапускает systemd-сервис, предварительно бэкапя текущий
бинарник и **автоматически откатываясь**, если новый не поднялся здоровым:

```
cd /root/OpenFlux && ./deploy/update.sh
```

Запускается вручную, когда сами решите обновиться — ничего на сервере само
не проверяет наличие обновлений.

### Консоль управления (как меню в 3x-ui)

[`deploy/menu.sh`](deploy/menu.sh) — интерактивная root-only консоль для
машины с `--role=exit-panel`: обновление, список/добавление/удаление
клиентов, включение/перенастройка/отключение Telegram-бота — всё одной
командой вместо curl+jq к API панели или ручного редактирования
systemd-юнита:

```
cd /root/OpenFlux && sudo ./deploy/menu.sh

# либо один раз сделать симлинк для короткой команды откуда угодно:
sudo ln -sf "$(pwd)/deploy/menu.sh" /usr/local/bin/openflux-ctl
sudo openflux-ctl
```

При первом запуске проведёт через настройку (адрес панели, логин/пароль,
пути к ключу/данным), автоматически подхватив их из уже существующего
systemd-override, если он есть. Состояние хранится в
`/root/.openflux-ctl.env` (root-only, `0600`) — тот же уровень доверия,
что и у systemd-юнита, где пароль панели и так лежит открытым текстом.
Любое изменение настроек Telegram-бота (и вообще всё, что трогает юнит)
полностью пересобирает `ExecStart` заново из этого состояния и
перезапускает сервис — так что никогда не остаётся наполовину
применённого ручного редактирования. Именно на этом легко ошибиться,
правя override руками в `nano`.

### Клиент - macOS utun (по умолчанию на macOS)

```
sudo ./openflux --role=client --inbound=tun \
    --transport=yandex \
    --url="YOUR_YANDEX_DOC_URL"
```

Создаёт utun-интерфейс, ставит bypass-маршруты для транспорта, ждёт
подключения транспорта, затем забирает default-маршрут. SOCKS5 не нужен.
Требует sudo. Весь трафик, кроме транспорта, идёт через туннель.

### Клиент - SOCKS5 (все платформы, fallback)

```
./openflux --role=client --inbound=socks5 \
    --transport=yandex \
    --url="YOUR_YANDEX_DOC_URL" \
    --socks5=:1080
```

Настройте браузер / приложение на `127.0.0.1:1080` как SOCKS5-прокси. Это
режим по умолчанию на всех платформах, кроме macOS.

### Выбор кодека

По умолчанию транспорт использует батчированный + zstd кодек
(`transport/batched.go` + `transport/framing.go`). Для старого per-packet
LZ4-кодека передайте `--codec=legacy`:

```
./openflux --role=client --codec=legacy ...
```

**Важно:** батчированный wire-формат НЕ совместим с legacy LZ4.
Клиент и выходная нода должны использовать один и тот же кодек (оба - новые,
либо оба - `--codec=legacy`).

### Шифрование (опционально)

Шифрованный транспорт - это Noise-handshake `NKpsk0` (X25519, AES-256-GCM,
SHA-256) между клиентом и выходной нодой, идущий по тому же каналу, что и
данные. У выходной ноды есть статическая пара ключей, клиенту нужен только её
публичный ключ. Каждый handshake даёт свежие сессионные ключи, клиент
повторяет его каждые 2 минуты по расписанию WireGuard, пока старая сессия
продолжает работать, поэтому утёкший позже ключ не раскрывает записанный
трафик. Кадры данных несут 64-битный счётчик: он служит nonce для AEAD и
питает скользящее окно anti-replay.

**Выходная нода:** выберите файл для статического ключа. Он создаётся при
первом запуске, публичный ключ печатается при старте:

```
./openflux --role=exit ... --exit-key-file=/etc/openflux/exit.key
```
```
=== EXIT PUBLIC KEY (generated and saved to /etc/openflux/exit.key) ===
<ключ в base64>
Start clients with --peer-key=<ключ в base64>
```

**Клиент:** передайте этот публичный ключ:

```
./openflux --role=client ... --peer-key=<ключ в base64>
```

**Закрытая нода (опционально):** общий секрет из 16+ символов в файле на обеих
сторонах подмешивается в handshake как pre-shared key. Клиентов без него
выходная нода молча игнорирует:

```
./openflux --role=exit   ... --exit-key-file=exit.key --psk-file=secret.txt
./openflux --role=client ... --peer-key=<ключ в base64> --psk-file=secret.txt
```

Замечания:
- Шифрованный слой стоит под кодеком: один AEAD накрывает целый батч, сжатие
  продолжает работать. Накладные расходы - 33 байта на батч.
- Один клиент на документ. Второй клиент, сделавший handshake в том же
  документе, забирает его себе (без шифрования он бы просто ломал трафик).
  Давайте каждому клиенту свой документ.
- Без флагов - без шифрования, поведение не меняется. Старый
  `--encryption-key-file` принимается как синоним `--psk-file`, но сам по себе
  шифрование больше не включает; wire-формат v1 не принимается.

### Мульти-стрим (несколько документов)

Передайте в `--url` список через запятую (`yandex`, `vyandex`), и один туннель
пойдёт сразу через несколько документов. Если документ умер или relay перестал
по нему доставлять, туннель продолжает работать через остальные (issue #50).
Клиенты панели (`--role=exit-panel`) тоже это поддерживают — то же значение
через запятую в поле URL клиента, в веб-интерфейсе или в Telegram-боте.

```
# выходная нода
./openflux --role=exit --mode=l3 \
    --url="https://disk.yandex.ru/i/AAA,https://disk.yandex.ru/i/BBB" \
    --multistream-status=10s

# клиент: те же документы, в любом порядке
./openflux --role=client \
    --url="https://disk.yandex.ru/i/BBB,https://disk.yandex.ru/i/AAA" \
    --multistream-status=10s
```

Как это работает:

- Каждый документ - полноценный отдельный стрим (транспорт, кодек,
  шифрование), поэтому по каждому идёт тот же wire-формат, что и с одним
  документом.
- Каждое TCP-соединение закреплено за одним документом, разные соединения
  распределяются по документам. Если размазать пакеты одного соединения по
  документам, они перемешаются, и скорость соединения обвалится.
- Документ считается рабочим, пока по нему приходят keepalive пира.
  Отключённый документ перестаёт получать трафик сразу; так же и документ, в
  списке участников которого остались только мы (пир вышел). Подключённый, но
  молчащий по другой причине (например, пир попал на другой backend документа) -
  через 25 с.
- Пакеты соединения отправляются через тот документ, по которому последний раз
  пришли его пакеты. Когда одна сторона переносит соединение на другой
  документ, вторая переезжает следом сразу, а не шлёт ACK-и в потерянный
  документ.
- С одним URL поведение в точности как раньше.

`--multistream-status` пишет одну строку за интервал:

```
[MULTI] connected=2/2 peer=1/2 s0[AAA]=UP(peer=3s,rx=812,tx=790,rc=0) s1[BBB]=NOPEER(peer=41s,rx=15,tx=9,rc=2)
```

`UP`: подключён, пир недавно был слышен; `NOPEER`: подключён, но пир молчит;
`DOWN`: не подключён. В iOS-клиенте впишите список через запятую в поле URL.

### Бенчмарки

Измерьте чистый goodput через транспорт, не задевая сеть хоста:

```
# Отправитель: залить 100 MB
./openflux --role=bench-send --bench-bytes=100 --transport=yandex --url="..."

# Приёмник: измерить goodput
./openflux --role=bench-sink --transport=yandex --url="..."
```

### Телеметрия трафика

Машиночитаемый трафик с фиксированным интервалом, прямо из собственных
счётчиков байт транспорта (не из системной статистики сети по приложению,
которая считает трафик всех приложений через VPN вместе):

```
./openflux --role=client --traffic-stats=1s ...
```

```
[TRAFFIC] connected=true tx=182933 rx=1044021
```

`connected` отражает реальное состояние — для зашифрованного транспорта это
означает подтверждённую Noise-сессию, а не просто живое соединение канала
под ней.

### Другие транспорты

```
# Yandex Volga (HTTP relay + WS)
./openflux --role=exit --mode=l3 --transport=vyandex --url="..." --debug

# MAX / OneMe (WebRTC DataChannel)
./openflux --role=exit --mode=l3 --transport=oneme \
    --maxToken="..." --maxUid="..." --debug

# Cups.online (Centrifugo-комнаты)
./openflux --role=exit --mode=l3 --transport=cupsonline --debug
# печатает base64-список комнат; передайте его клиенту через --url

# Mail.ru Docs (WS)
./openflux --role=exit --mode=l3 --transport=mailru \
    --url="YOUR_MAILRU_PUBLIC_LINK" --debug
# принимает как голый weblink (AbCdEfGh1/IjKlMnOp2), так и полный URL
# (https://cloud.mail.ru/public/AbCdEfGh1/IjKlMnOp2)
```

## Реализация собственных транспортов

Реализуйте интерфейс `Transport` из `transport/transport.go` и
зарегистрируйте свой транспорт в `switch`-блоке `main.go` (см.
`transport/mailru/` как полный пример). Батчированный кодек
(`BatchedTransport`) оборачивает любой транспорт - новый бэкенд получает
батчинг бесплатно.
